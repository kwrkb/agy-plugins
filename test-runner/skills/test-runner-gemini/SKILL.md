# Go test runner スキル

このスキルは、`test-runner` プラグインの `go_test` MCP ツールを使用して、Go モジュールのテスト実行、失敗原因の特定、および修正後の効率的な再実行を行うためのガイドです。

## 基本的な使い方

`go_test` を呼び出す際は、`go.mod` が存在するディレクトリの絶対パスを `module_path` に指定します。MCP サーバーのカレントワーキングディレクトリはリポジトリルートと異なる場合があるため、相対パスではなく絶対パスを推奨します。

- **`module_path`** (string, 必須): `go.mod` が置かれているディレクトリの絶対パス。マルチモジュール構成のリポジトリでは、対象モジュールごとに個別に呼び出します。
- **`packages`** (array of string, 任意): パッケージパターン。既定値は `["./..."]`。フラグや `.go` ファイル一覧の指定は不可。
- **`run`** (string, 任意): Go の `-run` 正規表現（サブテストの `/` 区切り構文に対応）。
- **`timeout_seconds`** (integer, 任意): パッケージ探索・コンパイル・テスト実行全体の上限時間（1〜300秒、既定60秒）。

## 実行結果の確認ポイント

返却される JSON オブジェクトから以下のフィールドを確認します：

1. **`status`**:
   - `passed`: 全テスト成功
   - `failed`: テスト失敗またはビルド失敗（MCP ツールとしては正常終了扱い）
   - `no_tests`: テスト実行対象が存在しなかった、または全件スキップ
   - `error` / `timeout` / `cancelled`: ツールエラー、タイムアウト、キャンセル中断（MCP の `isError` が true）
2. **`build_failures`**:
   - ビルド・コンパイルエラーの一覧とログ。テスト失敗件数とは別に報告されます。
3. **`packages`**:
   - パッケージ単位の結果一覧。`failures` 配列に失敗したテスト名とログが含まれます。
   - 個別のテスト名がつかない失敗（panic、セットアップ失敗、`TestMain` の異常終了など）は、パッケージログ（`log`）および `stderr` を確認します。
4. **`logs_truncated`**:
   - 返却ログ上限（64 KiB）に達してログが切り詰められた場合に `true` となります。必要な診断情報を得るには、対象パッケージやテストを絞り込んで再実行してください。
5. **`incomplete`**:
   - プロセス中断やタイムアウト等により結果が途中で切れている場合に `true` となります。

## 修正後の再実行（rerun オブジェクトの活用）

テストが失敗した場合、各失敗情報に `rerun` オブジェクトが含まれます。

- コード修正後は、失敗したテストの `rerun` オブジェクトをそのまま `go_test` の引数として渡すことで、該当テストのみをピンポイントで再実行できます。
- 親テストとサブテストの両方が失敗として報告されている場合、自動で両方を再実行するのではなく、目的に応じて適切な粒度（親全体か特定のサブテストか）を選択してください。

## 権限と実行環境に関する注意

- テストはサーバーホストの権限と Go 環境（`go.work`、`GOFLAGS`、ツールチェーン等）を継承してプロジェクトのコードを直接実行します。
- ファイルの書き込みや外部通信が発生する可能性があります。このツール自体はサンドボックスを提供しないため、現在のタスクの許可範囲内で実行してください。
